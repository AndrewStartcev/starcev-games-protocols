# 00 — Master Protocol

Версия: `1.0.0`  
Проверено: `2026-09-11`

## 1. Назначение

Этот документ задаёт обязательные правила для всех браузерных игр Starcev Games. Тематические документы уточняют правила, но не должны противоречить этому файлу.

Термины:

- **MUST / ОБЯЗАТЕЛЬНО** — нарушение блокирует milestone или релиз;
- **SHOULD / РЕКОМЕНДУЕТСЯ** — отступление допустимо только с зафиксированной причиной;
- **MAY / МОЖНО** — решение принимается по конкретной игре.

## 2. Базовый стек

ОБЯЗАТЕЛЬНО:

- Godot `4.7.2-stable` на дату этой версии протокола;
- GDScript;
- Web export;
- renderer `Compatibility` / WebGL 2.0;
- single-thread Web export;
- `index.html` как точка входа;
- Git с понятными атомарными коммитами.

Версия движка закрепляется в `docs/PROJECT_STATE.md` конкретной игры. Обновлять minor/major версию Godot посреди проекта без причины нельзя. Patch-обновление допускается после отдельного web smoke test.

## 3. Главные продуктовые ограничения

Игра должна:

1. быть понятной в первые 10–30 секунд;
2. работать мышью и touch, если жанр физически позволяет;
3. не зависеть от hover для обязательных действий;
4. иметь достаточную длительность или реиграбельность;
5. иметь естественные точки для монетизации, а не искусственно ломать gameplay ради рекламы;
6. переживать потерю сети и недоступность SDK настолько, насколько это возможно;
7. не терять прогресс при обычном перезапуске;
8. корректно ставиться на паузу и глушить звук при рекламе/скрытии вкладки;
9. не содержать незавершённых экранов, заглушек и debug UI в release build;
10. иметь реальный web QA, а не только запуск из Godot Editor.

## 4. Архитектурные правила

- Gameplay не вызывает API Яндекса/Пикабу напрямую.
- Платформенные вызовы проходят через единый слой `Platform`/`PlatformService`.
- Сохранения проходят через `SaveService`.
- Реклама проходит через `AdsService`.
- Аудио проходит через `AudioService`/аудио-шины и единое состояние паузы.
- Игровые сцены по возможности самодостаточны и слабо связаны.
- Глобальные Autoload используются только для действительно глобальных и изолированных сервисов.
- Новая механика не должна размазывать платформенный код по сценам.
- GDScript по умолчанию статически типизирован там, где это не мешает скорости прототипирования.

## 5. Web-правила

По умолчанию:

- threads: OFF;
- PWA: OFF для платформенных билдов;
- GDExtension: OFF, если не доказана необходимость;
- внешние web-зависимости: минимум;
- браузерный scroll/overscroll/swipe-to-refresh не должен вмешиваться в игру;
- звук не стартует принудительно до допустимого пользовательского взаимодействия;
- fullscreen/cursor capture вызываются только из user gesture, если используются.

Причина single-thread: web multithreading требует SharedArrayBuffer/cross-origin isolation, что конфликтует с рекламными и сторонними интеграциями и ухудшает совместимость web-паблишеров.

## 6. Контент и графика

Нельзя начинать массовое производство финальных ассетов, пока не подтверждены:

- core loop;
- структура основных экранов;
- реальные размеры UI-слотов;
- `ASSET_MANIFEST`.

Концепт задаёт art direction. Концепт не является production UI.

Production asset должен иметь:

- точный путь;
- назначение;
- размер/соотношение сторон;
- формат;
- alpha/no-alpha;
- stretch mode;
- 9-patch margins при необходимости;
- safe area;
- правило по встроенному тексту.

## 7. Реклама

- Rewarded — только после явного действия пользователя и понятного обещания награды.
- Награда выдаётся только после подтверждённого успешного rewarded.
- Fullscreen — только в естественной паузе: конец раунда, переход уровня, возврат в меню и аналогичное.
- Во время рекламы gameplay, input и игровой звук блокируются.
- После рекламы восстанавливается предыдущее состояние, а не безусловно запускается игра.
- Двойной/параллельный вызов рекламы запрещён.

## 8. Сохранения

- Local-first: изменение состояния сразу фиксируется локально.
- Cloud sync — отдельно, с debounce/batching.
- Нельзя отправлять облачное сохранение на каждое нажатие/монету/кадр.
- Save schema всегда содержит версию.
- Миграции между версиями save обязательны после публикации.
- Не доверять клиенту в вопросах денег/покупок, если появляется backend или реальные платежи.

## 9. Definition of Ready для разработки

До начала полноценной реализации должны существовать:

- `GAME_BRIEF.md`;
- оценка Production Score;
- краткий GDD;
- описание core loop;
- monetization hypothesis;
- scope первой версии;
- целевые устройства и ориентация.

## 10. Definition of Ready для арта

До финального арта:

- graybox/prototype работает;
- UX основных экранов понятен;
- `ASSET_MANIFEST.md` заполнен;
- утверждён art direction/reference;
- перечислены dynamic text и baked text;
- определены реальные display rect и stretch rules.

## 11. Definition of Done для релиза

Релиз блокируется, если хотя бы один пункт не выполнен:

- основной игровой цикл работает от старта до результата;
- нет blocker/critical багов;
- resize не ломает UI;
- mobile + desktop input проверены;
- сохранение/загрузка проверены;
- platform init корректен;
- реклама не ломает состояние;
- mute/pause работают;
- браузерная консоль не содержит необработанных ошибок;
- release build протестирован в целевой платформе/draft;
- платформенный checklist закрыт;
- promo assets соответствуют фактической игре;
- `RELEASE_REPORT.md` заполнен.

## 12. Stop-the-line

Агент обязан остановить следующий этап и исправить причину, если:

- core loop неинтересен/непонятен;
- финальная графика не совпадает с реальной компоновкой;
- SDK ломает локальный запуск;
- save может потерять прогресс;
- реклама может выдать награду без просмотра;
- игра не работает с недоступной рекламой;
- UI обрезается на заявленных экранах;
- билд превышает платформенные ограничения;
- новый код создаёт повтор уже решённой общей проблемы.

## 13. Приоритет решений

При конфликте целей порядок такой:

1. игра не ломается;
2. игрок понимает, что делать;
3. прогресс не теряется;
4. загрузка и FPS приемлемы;
5. визуал качественный;
6. монетизация встроена без разрушения retention;
7. архитектура остаётся поддерживаемой;
8. только затем дополнительная полировка.
