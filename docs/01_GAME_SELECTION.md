# 01 — Выбор игры и Production Score

Цель — не запускать в производство каждую «прикольную» идею. Игра должна иметь шанс окупить время разработки и пополнить портфель.

## 1. Классы проектов

### A — Factory

Срок-ориентир: 2–5 рабочих дней до release candidate.

Примеры: clicker/incremental, solitaire, mahjong, sorting, simple puzzle, tile/merge, компактные idle-механики.

Требование: минимум уникального технологического риска, много переиспользуемых решений.

### B — Premium Casual

Срок-ориентир: 5–10 рабочих дней.

Примеры: сюжетная косынка, tycoon с мета-прогрессом, word game с главами, более насыщенный puzzle.

Требование: дополнительное качество визуала/контента должно улучшать retention или органический потенциал.

### C — Experiment

Новая/рискованная механика, необычный 3D или нетипичный UX.

Правило: сначала дешёвый playable prototype, затем решение `GO / PIVOT / KILL`.

Рекомендуемая структура портфеля на этапе масштабирования: примерно `60% A / 30% B / 10% C`, корректируется данными.

## 2. Production Score

Каждый критерий оценивается `0–5`.

| Критерий | 5 баллов |
|---|---|
| Core loop clarity | понятен без объяснений за 10–20 сек |
| Desktop fit | естественно и приятно играется мышью |
| Mobile fit | естественно и приятно играется touch |
| Replayability/content | 30+ минут или сильная реиграбельность |
| Progression | понятный рост/цели/открытия |
| Rewarded fit | 2+ добровольных полезных сценария |
| Fullscreen fit | есть естественные паузы |
| Asset cost | мало дорогих уникальных ассетов |
| AI production fit | ассеты/контент можно производить стабильно |
| Time to release | реалистично уложиться в класс проекта |
| Technical risk | нет сложного backend/physics/network риска |
| Portfolio novelty | не каннибализирует портфель без причины |

Максимум: 60.

Рекомендация:

- `48–60` → GO;
- `40–47` → GO только после устранения слабых мест;
- `32–39` → prototype only;
- `<32` → не производить сейчас.

Production Score — фильтр, а не гарантия дохода.

## 3. Обязательная monetization hypothesis

До кода ответить:

- зачем игрок вернётся;
- где естественно предложить rewarded;
- где допустим fullscreen;
- какая прогрессия поддерживает длинную сессию;
- что игрок получает через 1, 5, 15 и 30 минут;
- есть ли причина играть второй день.

Нельзя проектировать core loop вокруг обязательной рекламы.

## 4. Desktop не вторичен

Для Пикабу desktop — полноценный целевой сегмент. Платформа указывает примерно 50% desktop, 40% mobile и 10% другое. Поэтому mobile-first не должен означать «desktop как растянутая версия телефона».

Проверять:

- комфортный размер игрового поля на 16:9;
- hover states как улучшение, но не обязательная механика;
- drag/click с мышью;
- отсутствие гигантских мобильных элементов на desktop;
- нормальную плотность информации.

## 5. Kill criteria

Проект закрывается или радикально упрощается до финального арта, если:

- core loop не хочется повторить после 3–5 минут;
- управление требует длинного обучения;
- стоимость ассетов растёт быстрее ценности игры;
- без тяжёлого backend игра не работает, а backend не нужен бизнес-модели;
- web performance не достигает приемлемого уровня после разумной оптимизации;
- идея требует объёма контента, который невозможно произвести в срок;
- монетизация возможна только через раздражающие прерывания.

## 6. После релиза гипотеза проверяется данными

Через 1/3/7/30 дней сравнить прогноз с:

- players;
- sessions/player;
- avg session;
- playtime/player;
- ad requests/impressions;
- rewarded/player;
- fullscreen/player;
- show rate/fill;
- revenue/player;
- development time;
- revenue per development day.

Победителей масштабируем, проигравшие не получают бесконечную полировку без данных.
